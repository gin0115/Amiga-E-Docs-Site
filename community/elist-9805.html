EFindHit will need debug hunks as one to work.

One thing to watch with patches: stack usage.  A system patch means your
code
will be running on the caller's context, so try to avoid putting too much
stuff
on the stack - allocate memory for them as needed.

Watch out too for trashed registers.

>  LONG-READ from 00000018                        PC: 103891FA

Such a hit usualy mean you have an un-initialized structure, and you tried
to
access a pointer (or any other LONG) at offset 18.  Look for any object or
OS
structure that you could be accessing an item at this offset.

One hint for those system patches: use kprintf() from amigalib/debug.m.
This
will allow getting some output even if your caller is a task.

Speaking of this, make sure your patch code doesn't do any DOS calls unless
you
KNOW it's safe, since a calling task cannot access DOS.  An example is
Delay()
which will die when called on a Task context.

- - Have you used debug/kprintf to print out the values of all the
  variables/dereferences you make? This is by far the safest way, and if you
  go overboard you can write every executed line of your source code again
  with the values it is using again.

- - Remember you can't use anything that throws exceptions out of the patch
  procedure, always use HANDLE on your patch procedure, best not to use
  any exception-handling (directly or indirectly, eg NewR()) at all.

- - Remember that not only are patches called from an entirely different
context
  than the normal E code. A different process cannot use your stdin/stdout.

- - Remember tasks can also call system functions, and they cannot call
  dos.library at _all_. Therefore, _you_ may not call dos.library unless you
  check process.task.ln.type = NT_PROCESS. Better still, avoid dos like the
  plague, and instead use exec messages to communicate to another running
  process you set up to do the dos IO.

- - Remember that any patch you write will _increase_ the stack usage of all
  programs which call that function. Don't DEF complete structures or
estrings
  or lists/arrays, always use pointers to allocated memory. (Or if you were
  patching, say, AllocMem(), use semaphore-protected global space.)

- - Remember that any one time, more than one task can be calling the same
  function (concurrency). If you use global structures, protect them with a
  semaphore.

- - Some functions are marked as safe to be called from interrupts - in this
  case, you have to handle the possible deadlock that may occur (interrupt
  blocks task, then goes into a loop that waits for the blocked task to
  finish, which it will never do.)

- - Remember that trashing A4/A5 is fatal to E (save these registers if you
  touch them).

- - You must supply _all_ the correct registers to the patched function.
Load
  them explicitly with inline assembler. Do _not_ rely on E leaving those
  registers alone.

- - Remember to save _all_ registers as part of your assembler stub before
you
  call the E function itself. Never patch E functions directly in place.

- - Always allocate new MEMF_PUBLIC memory for each patch you make. Don't
free
  this memory until you are _sure_ noone is calling the patch.

- - Also ensure that you don't trash registers by calling the replaced
function
  like this:

        original := SetFunction( ..  {blahpatch} .. )

        [in blapatch():]
        original()

  E does not tell you, but it actually does this:
        MOVE.L  original, A1
        JSR     (A1)

  obviously, if one of your parameters was A1, you've just lost it.
  instead, do it yourself with inline asm:

        MOVE.L  original, A3
        JSR     (A3)

  or, if A0 to A3 are tied up as function parameters (like
EasyRequestArgs()),
  save A4 and recycle that:

        MOVE.L  A4, -(SP)
        MOVE.L  original, A4
        JSR     (A4)
        MOVE.L  (SP)+, A4

  don't use A5 for this purpose, if A0 to A4 are in use, then patch the
address
  directly into a JSR $xxxxxxxx. Remember to flush the caches before anyone
can
  call this.

- - Remember to check the OS function's autodocs for defined side effects
that
  you must.

- - A good debugging tip is to write a small assembler program to make an
example
  call to the patched function. You can then use an assembler monitor (such
as
  the spanky one in the new ASM-Pro, or trusty old Monam2 - this will show
you
  exactly what your E code is up to.

- - Take a look at Aminet:util/boot/MemPatch.lha
  I wrote the patch.m module included with it, sadly I didn't have time to
  write some autodocs for it, but MemPatch itself should serve as an example
of
  usage.

  The only unimplemented thing in is that I do not check if 'enough' stack
  space is left in the calling task's context before calling the E function.

Sitsofe K Wheeler wrote:
>
> Could anyone tell me how to pop up an ASL Screenmode requester from MUI?

This is an part of my screenModePopUp-mcc and probably a bit overscaled
for
your needs but it shows the possibilities of popasl.
All you need is to supply the start- and stop-hooks but it is
recommended to use
a custom class.

Called with attributes (MUIA_Popstring_String and ..._Button):

     MUIA_Popstring_String, TextObject,
         TextFrame, TextBack,
     End,
     MUIA_Popstring_Button, TextObject,
         ButtonFrame, ButtonBack,
         MUIA_CycleChain, 1,
         MUIA_Text_Contents, 'Select...',
         MUIA_Text_PreParse, '\ec',
         MUIA_Text_SetMax, MUI_TRUE,
         MUIA_InputMode, MUIV_InputMode_RelVerify,
     End

/* Father: MUIC_Popasl
*/
PROC screenModePopup_New(cl:PTR TO iclass,obj:PTR TO object,msg:PTR TO
opset)
- ->// "NEW OF screenModePopup"
DEF data:PTR TO screenModePopup_data

  IF obj:=doSuperNew(cl,obj,
     [
      MUIA_Popasl_StartHook, gethook({hook_StartAslScreenMode},
{startAslScreenModeFunc}),
      MUIA_Popasl_StopHook,  gethook({hook_StopAslScreenMode},
{stopAslScreenModeFunc}) ,
      MUIA_Popasl_Type,      ASL_SCREENMODEREQUEST,
      -> you can add any ASLSM_xxx-tags here. It is like
AllocAslRequest().
      TAG_MORE,msg.attrlist
    ])

    -> ...

    RETURN obj
  ENDIF

ENDPROC NIL
- ->\

- ->// "Hooks OF screenModePopup"
PROC startAslScreenModeFunc(popobj:PTR TO object,taglist)
DEF tagi:PTR TO tagitem,
    data:PTR TO screenModePopup_data

  data:=OCLASS(popobj)
  data:=INST_DATA(data,popobj)

  IF tagi:=taglist
    WHILE tagi.tag<>TAG_DONE DO tagi++          -> find end of taglist,
see MUIA_Popasl_StartHook

    -> attach our own taglist to initialize the requester (optional),
NEW is
    -> essential otherwise you side effects will occur
    -> passed to Aslrequest()

    tagi.tag:=TAG_MORE
    tagi.data:=NEW [ASLSM_INITIALDISPLAYID,
getBestModeID(data.displayid,data.width,data.height,data.propflags,
data.propmask),
                    ASLSM_INITIALOVERSCANTYPE,  data.overscantype,
                    ASLSM_INITIALDISPLAYDEPTH,  data.depth,
                    ASLSM_INITIALDISPLAYWIDTH,  data.width,
                    ASLSM_INITIALDISPLAYHEIGHT, data.height,
                    ->ASLSM_SCREEN,               getApplicationScreen(),
                    ASLSM_WINDOW,               getApplicationWindow(),
                    TAG_DONE,0]

    -> remember the dynamical created taglist
    set(popobj, MUIA_UserData, tagi.data)
  ELSE
    RETURN FALSE
  ENDIF

ENDPROC MUI_TRUE

PROC stopAslScreenModeFunc(popobj:PTR TO object,aslreq:PTR TO
screenmoderequester)

  -> Dispose our taglist
  FastDisposeList(xget(popobj, MUIA_UserData))

  -> set new values, so you can setup notifications on it
  newSetAttrsA(popobj, NEW [MUIA_ScreenModePopup_Width,
aslreq.displaywidth,
                            MUIA_ScreenModePopup_Height,
aslreq.displayheight,
                            MUIA_ScreenModePopup_Depth,
aslreq.displaydepth,
                            MUIA_ScreenModePopup_DisplayID,
aslreq.displayid,
                            MUIA_ScreenModePopup_OverscanType,
aslreq.overscantype,
                            TAG_DONE,0])

  -> update the string gadget
  newDoMethodA(xget(obj,MUIA_Popstring_String),
               NEW [MUIM_SetAsString, MUIA_Text_Contents,
                    '%ld%ld%ld',

aslreq.displaywidth,aslreq.displayheight,aslreq.displaydepth])

ENDPROC

When your executable gets to 32k in size the compiler will moan that
references are outside the 32k range, then put OPT LARGE in your code
so that references are now outside 32k. OPT LARGE does a load of
internal stuff that no-one has yet adequatly(sp?) explained.

> PROC main() HANDLE  (I know what PROC main() is, what is HANDLE for?)
>
> EXCEPT

These are for exceptions:

PROC main() HANDLE -> tell this proc to handle exceptions.
        WriteF(`This line gets executed.\n`)
        Raise("NO") -> Raise an exceotion.
        WriteF(`This line never gets executed!\n`)

EXCEPT -> This is the exception handler.

        /* When you call Throw() The code comes here, the value of
        your exception is held in a special variable called `exception`
        you can do a simple SELECT..CASE..ENDSELECT to test which error
        it is: */

        SELECT
        CASE "NO" ; WriteF(`An exception occured, of the NO type.\n`)
        CASE "MEM" ; WriteF(`An MEM exception occured\n`)
        CASE "NIL" ; WriteF(`uninitialised pointer is being used.`)
        ENDSELECT

        /* It is useful to put your clean up code here, to deallocate
        mem, windows, etc... but we would need to change EXCEPT to
        EXCEPT DO, as if there was no exception raised the code would
        end at EXCEPT, and none of the code below EXCEPT would be
        executed. */
ENDPROC

You aren`t limited to using the special constants "????", you can use
normal constants, variables, and even strings, eg:

Raise(`An error occured`)
EXCEPT
WriteF(`error:\s\n`, exception)

It can get more complicated than that, as every PROC can have an
exception handler, and you can parse errors at different levels of your
code, and the ReThrow() it back up to higher code...

Also theres the exceptioninfo variable which you can also send along
with the exception, the exception info can contain whatever you want,
eg/ a filehandler that needs freeing, the window which caused the
error, the line number, an error description etc...

Exceptions are one of the very best things about AmigaE, and they`re
the reason I use AmigaE.

Hope this is helpful.

> Except in certain specific circumstances, the use of p[] rather

Using p[] is called defrencing an array. This means that an invisble
pointer knows which array you are currently on. For example:

a:=A[]
is the same as
a:A[0] (Do arrays start at 0?)
unless you have done some thing like:
A[]++
In which case
a:=A[]
will be the same as
a:=A[1]

Occasionally you may which to pass a variable by reference. Instead of
just passing the variable, you can pass its location in memory. This
done like so:
dumbproc({a})
This passes the address of the variable. To find out the value at a
particular address a '^' is used:
<inside dumbproc(a)>
b:=^a (otherwise the address will be inserted into b).

^a:=b
Is kind of the reverse and will now put the value of b into a
(remember, a is still an address). If you look at a in the original
procedure you will find that's its value has changed.

There are way better examples of the above inside
dev/e/BeginnersGuide.lha on the Aminet.

That's not the point of OSVERSION.
You are meant to look at each AmigaOS call from dos, exec, intuition and
graphics you make, and read its autodocs.
If one of those autodocs says (V36) in the title, you must use OSVERSION 36.
If one says (V37), use OSVERSION 37.

It's so you don't accidentally run on a system where the OS is too old - for
example, AllocVec() is 36+ only.

OSVERSION only affects the version numbers used on E's startupcode
OpenLibrary()s for those 4 libraries (might also affect generated code
for builtins some day soon).

You yourself are meant to use the right version number when
opening other libraries, NEVER 'just use 0'.

As for the version numbers:

0-32 only exist in prehistoric Amigas. Not supported by
Commodore Amiga or anyone else for quite some time.

33 = Workbench 1.2
34 = Workbench 1.3
35 = Workbench 1.3, with hires monitor support (not generally released)

36 = Workbench 2.0 (only in some A3000s)
37 = Workbench 2.04
38 = Workbench 2.1 (disk only, no v38 ROM libraries)

39 = Workbench 3.0
40 = Workbench 3.1
41 = Workbench 3.1 with multibyte char support
42 = The next big thing... current (unreleased) OS version level.
     Library writers (especially the datatypes ones) use it to
     look trendy.

Note that these version numbers don't 'guarantee' a 'Workbench' version -
they
refer only to the major version of the ROM and the libraries within.
Disk-based
libraries generally use the same version numbering for their releases.

AllocMem(size,flags) takes two arguments, size and flags. Size is
the number of bytes you want and with flags you can choose
which memory type you want, cleared or not cleared, public or
not public. It returns the allocated memory which MUST be freed
with FreeMem(memory,size). BTW watch out for freeing memory
twice(CRASH!). Example:

mem:=AllocMem(243,MEMF_FAST)
....
FreeMem(memory,243)

mem:=AllocMem(500,MEMF_PUBLIC OR MEMF_CLEAR OR MEMF_CHIP)
...
FreeMem(mem,500)

The MEMF_* constants can be found in emodules:exec/memory.m
and they are decribed in the autodocs in exec/AllocMem() (Amazing!)

You can use ReadStr() (internal function) or Fgets() (dos function).
ReadStr() is unbuffered and slow while Fgets() is buffered and kinda
fast so you should probably use Fgets(). They are used like this:

ReadStr(handle,str)

For example ReadStr(stdout,mystr). It returns -1 if end of file or
error.
str does not end with a linefeed

Fgets(handle,str,length)

For example Fgets(stdout,mystr,1024). Returns 0 when end of file or
error(i think). str ends with a linefeed

Here is an small example:

PROC main()
DEF input,line
IF input:=Open(arg,OLDFILE)
- ->     WHILE ReadStr(input,line)<>-1
- ->     str[StrLen(str)]:="\0"    -> Add a linefeed
- ->     ^^^^^^^^^^^^^^^^ Only if you use ReadStr()
        WHILE Fgets(input,line,1024)
                WriteF(line)

Here's an excerpt from the (soon to be) aminet file dev/e/DiskFile.lha

OBJECT device_info
  name, device, unit  -> 'DF0:', 'trackdisk.device', 0
  lowcyl, highcyl     -> 0, 79
  trksize, sides      -> 5632, 2
ENDOBJECT

PROC create(drivename) OF device_info HANDLE

  -> the DEVICE_INFO object is purely a read-only information structure,
  -> only the constructor and destructor are necessary.
  -> we pass in a device name ('DF0:', 'ram', 'Dh0', etc...) and
  -> get out the information about that device, or an "ndev" exception

  -> Note how all the possible exceptions are sandwiched between the
  -> LockDosList() and the UnLockDosList() in the handler. This is
  -> essential, as we cannot allow any DOS calls without unlocking
  -> the dos list, or the system will hang.

  DEF dl:PTR TO doslist, fssm:PTR TO filesysstartupmsg,
      de:PTR TO dosenvec, devname=NIL, pos, found=FALSE

  dl:=LockDosList(LDF_DEVICES OR LDF_READ)

  -> get name of device (without ending in ':')
  devname:=strdup(drivename)
  IF (pos:=InStr(devname,':'))<>-1 THEN devname[pos] := "\0"

  -> use this to find the disk device
  IF dl:=FindDosEntry(dl,devname,LDF_DEVICES)
    IF dl.type=DLT_DEVICE

      -> we found the entry we wanted. Copy relevant information
      found:=TRUE

      -> convert dl.name=BSTR('DF0') to self.name='DF0:'
      drivename := BADDR(dl.name)
      self.name := String(Char(drivename)+1)
      StrCopy(self.name, drivename+1, Char(drivename))
      StrAdd(self.name, ':')

      -> filesystemstartupmsg holds all information about the
      -> diskdevice underneath the handler

      -> device and unit are used for call to OpenDevice()
      fssm         := BADDR(dl::devicenode.startup)
      self.device  := strdup(fssm.device,BSTR)
      self.unit    := fssm.unit

      -> diskenvironment holds the drive geometry - start and end
      -> cylinder, number of surfaces, size of track (in blocks),
      -> size of blocks (in longwords - *4 to get size in bytes)

      de           := BADDR(fssm.environ)
      self.lowcyl  := de.lowcyl
      self.highcyl := de.highcyl
      self.sides   := de.surfaces
      self.trksize := Mul(BADDR(de.sizeblock),de.blockspertrack)
    ENDIF
  ENDIF

  IF found=FALSE THEN Raise("ndev")

EXCEPT DO
  UnLockDosList(LDF_DEVICES OR LDF_READ)
  free(devname)
  ReThrow()
ENDPROC

PROC taskname(p:PTR TO process)
  -> return the name/len of task/process p,
  DEF cli:PTR TO commandlineinterface, name:PTR TO CHAR

  IF p.task.ln.type = NT_PROCESS THEN
    IF cli := BADDR(p.cli) THEN
      IF name := BADDR(cli.commandname) THEN
        IF name[] THEN RETURN name+1, name[]

  IF name := p.task.ln.name THEN

  StringF(unknown, 'Unknown @ 0x\z\h[8]', p)

No, it's a completely undocumented "feature" of method calls in BOOPSI.
As far as I can tell, you basically don't own the message you send.
That is, Intuition feels completely at liberty to alter the message
after you've sent it.  In fact, Intuition even uses your messages to
send *its* own messages!

Anyway, what this means is that the contents of your messages may be
altered so you can't just use a static list for them.  If you do use
a static list, then you'll need to assign the correct values to the
list elements using explicit assignments (like those above), because
the second time you use the list (and make the method call) your
list will have the values the last call altered them to...

> 2) Is there a more elegant way of avoiding this problem or are the
> ways shown above in this program the best solutions?  A
> dynamically allocated list instead of a static one?

There are lots of ways of doing it.  The main thing to be aware of is
that BOOPSI feels free to alter your messages.  So you need to be sure
you anticipate this.  And it's not just a matter of which calls alter
messages at the moment: future versions of BOOPSI may well decide to
alter more method messages.

Basically, what you need to do is be sure the message you send contains
the right data.  You can allocate it statically, dynamically or on the
stack (local var).  But if you do it statically you need to make sure
the message has not been used before or that you've explicitly copied
the correct data into it.

> I have several spots in my Boopsi gadget that need a GM_RENDER message
> sent, and that first method above seems so un-E-like.  I'd really
> prefer to use a list.

By all means dynamically allocate it.  What NEW <list> will do is create
a new slab of memory and copy the contents of <list> to it.  This way
the <list> will not be altered by any method calls, so the contents will
be the same next time the NEW <list> is executed.  Just remember to
deallocate the result of NEW after the method has been executed (i.e.,
don't assume you can reuse the message without first copying the correct
data into it, because it won't be the same as <list> any more).

The reason that NEW was not used in those RKRM examples is because at
that time there was no FastDisposeList()...

I recommend to *always* use dynamical lists. MUI does the
same nasty things with taglists, eg. filtering by replacing
tags with TAG_IGNORE etc., as in C taglists are always created
on stack.
Also remember that static list may be overwritten by your program/
classes, simply by recursive calls. This can happen for example
if you call set() within your set-method (Note: set() is defined
as SetAttrsA(obj, [attr, value, TAG_DONE, 0]).
I use replacements for all set/doMethod/... funcs.
For example:
  PROC newDoMethodA(obj, dynamtags)
    obj:=doMethodA(obj,dynamtags)
    FastDisposeList(dynamtags)
  ENDPROC obj
  PROC newSetAttrsA(obj, dynamtags)
    obj:=SetAttrsA(obj,dynamtags)
    FastDisposeList(dynamtags)
  ENDPROC obj
  ...
Just call it with newDoMethodA(obj, NEW [...]:tagitem).
It may seem to be a huge overhead but it's error prone
(do you really know, or wanna know (?), what all those
BOOPSI classes do inside) and for an GUI it is fast enough.

Second, many people ommit the >,0< after an TAG_DONE/TAG_END.
Never do this! Just remember, that the initial examples are
written in C, where all tags are passed to an stack-arg
function or taglists are allocated via AllocTagItem() (??).
In both cases the *extra* (not useless) LONG *is* allocated.
I don't know if it matters in standard BOOPSI classes but I
have seen MUI-Programs becoming suddenly very stable just by
adding those little >,0< behind the TAG_DONE's.
So either use typed lists ([..,TAG_DONE]:tagitem) or add
the zero ([...,TAG_DONE,0]).

Hopefully this helps yout not to make the same bad
experiences with all that BOOPSI stuff.

PROC domsg_complilationwindow()
DEF imsg:PTR TO intuimessage, iaddress:PTR TO gadget, c=0

    WHILE imsg:=Gt_GetIMsg(complilationwindow.userport);
            IF imsg.class=IDCMP_CLOSEWINDOW;
                IF imsg<>0 THEN Gt_ReplyIMsg(imsg);imsg:=0;
                closecomplilationwindow()
                RETURN 0;
        ENDIF
        IF (imsg.class=IDCMP_GADGETUP) OR (imsg.class=IDCMP_GADGETDOWN)
            iaddress:=imsg.iaddress;
            c:=imsg.code

            IF imsg<>0 THEN Gt_ReplyIMsg(imsg);imsg:=0

            IF iaddress.gadgetid=BUNREF THEN openunrefwindow()

            IF iaddress.gadgetid=BVIEW
                IF imsg<>0 THEN Gt_ReplyIMsg(imsg);imsg:=0
                view_source()
            ENDIF
            IF iaddress.gadgetid=BRUN
                IF imsg<>0 THEN Gt_ReplyIMsg(imsg);imsg:=0
                run_prog()
            ENDIF
            IF iaddress.gadgetid=BEDIT
                IF imsg<>0 THEN Gt_ReplyIMsg(imsg);imsg:=0
                edit_source()
            ENDIF
            IF iaddress.gadgetid=BSHOWBUF
                IF imsg<>0 THEN Gt_ReplyIMsg(imsg);imsg:=0;
                openshowbufwindow()
            ENDIF

        ENDIF

        IF imsg<>0 THEN Gt_ReplyIMsg(imsg);imsg:=0

    ENDWHILE
ENDPROC

Well, the thing is, SELECT is a special kind of construction for comparing
one
variable to a load of different values. IF is a very general decision-making
(comparison/branch) construct.

I can guarantee you will use IF a lot more than you'll use SELECT. But if
what
you are doing is

IF x = 1 THEN ..
ELSE IF x = 2 THEN ...
...

then you are better to use a SELECT/CASE construction, because it is shorter
and neater.

For example, you could do a FOR loop like this:

FOR x := 1 TO 10 DO blah(x)

or

  x := 1
again:
  blah(x)
  x := x + 1
  IF x <= 10 THEN JUMP again

But clearly the FOR loop is much more readable than the IFs and JUMPs.
The idea behind high-level languages is that they provide constructs that
allow you to do very common operations in a efficient, and understandable
way.
