In this distribution of GenCodeE, you will find two GenCodeE: version 1.7 and version 2.2. The first generates code for Amiga E v2.1b and second for Amiga E v3.0b+. Being given that Amiga E v3.0 is a major update compared to Amiga E v2.1b, it seemed necessary to make two generation modules a separate code. In the future, all future GenCodeE number version 1.x will generate code for Amiga E v2.1b and those of version 2.x of the code for Amiga E v3.x. The codes generated by these two modules are not fundamentally different, but version 2.x makes maximum use of the new possibilities of Amiga E v3.0, Note the "object oriented" aspect.

Making such a code generator is particularly delicate. In effect, the generated code must be as perfect as possible to avoid the programmer to retouch it, but still readable in case a It would still be indispensable. After a lot of testing, Thinks of having reached a fair balance. However, I have not yet could really test the code generated by these new GenCodeE on a large scale application, so we must probably still be able to improve details. Do not hesitate to submit your comments and your suggestions (see author).

Finally, you will need Mac2E (v4.0+ recommended) to use the generated code and in addition to PPE (recommended v1.4d) for GenCodeE v1.7. These two programmes are available in the collections of the domain public. If you don't have them, stop reading here, and Get them. Similarly, FlexCat (also available in public) is very strongly advised to automatically generate the code for location, but it is not indispensable. Finally, AutoBuild (also available in the public domain) is an excellent Replacement of Build for Amiga E v3.0 users.

The code generated by GenCodeE is now too complex for simply describe its functioning. So I chose an example (significant) to present it rather than long (and painful) explanations. Let's first see a small tutorial on use Deft II. Then let us go on to this serious and fundamental question: But how does the author himself use his program? :)

Open the only window in Deft II. This is grossly broken down in three parts:

  • on the left the group 'Default Tools'
  • on the right the group 'Chemins'
  • bottom the text gadget 'File' and the group 'Deft Control'

The 'Default Tools' group is used to define the tools by default that Deft II will have to replace, and what new default tools He'll have to replace them. Each old/new default tool torque is displayed in this order in the list. To return such a group, use both gadgets chains 'Old' and 'New'. Note that this is typing on input in the text gadget 'New' that validates a couple. Note also that Deft It does not accept a torque if the old default tool is empty or if it already exists a couple with the same old default tool. However, it is quite possible to return a couple whose new tool by default is empty. It will then be displayed in italics in the list for you indicate that the definition of torque is incomplete.

The old default tool can include jokers (not the new Of course!). For example, "#?more#?" is an old default tool to valid fact. During the replacement phase, Deft II will look for all the path project icons to examine if one has a tool by which corresponds to this reason, and will perform in case of correspondence the replacement. You can easily replace "c/more", "c:more" and others ":c/MuchMore" by "c:most"! Even better, you can without fear ask to replace all the "#?guide#?" with "c:AmigaGuide" because Deft II checks before a replacement that it will not replace a chain by itself. So, a default tool like "C:amigaguide" (note Deft II does not distinguish between upper and lower case capitals), will not be replaced while ":c/AmigaGuide" will be.

The popup gadget on the right of the 'New' gadget opens a small list where all the new default tools already entered in Deft II: it avoids you to retread them. But the first time, you can use the "popfile" gadget to the right of the "popup" gadget. This opens up a file query where you can choose a new default tool.

By double-clicking on a couple in the list, you can edit This one.

Finally you can drop on the 'New' channel of the 'Tools by default' a tool icon. If you do, this one will appear in This chain. This has the same effect as the popfile gadget to the right of This chain.

The 'Chemins' group serves to define all the paths to examine recursively for replacement, paths which are grouped in a list. If you throw an icon in this group, the file path or the drawer is added to the list of paths. Double-click a path in the list also allows to edit it.

Finally, you use the group 'Deft II Control' to launch the replace default tools (button 'Start'), stop this replace at any time (button 'Stop') or save preferences (button 'Save prefs'), preferences that group the content of both lists. During the replacement phase, Deft II displays in the gadget string 'File' all files whose icon it changes.

I personally configured Deft II to use it in the case of a replacement on my hard drive. In other words, the preferences I have saved contain all my partitions in the path list.

However, a frequent case where default tool replacement is necessary appears when testing a new program (something I do in principle in RAM: or SD0:). Indeed, it is not uncommon that when I click on the installation icon or on the documentation icon, the Workbench does not find the default tool. To remedy this problem, I launches from the beginning of my Deft II tests with a "hotkey" from Tool- Manager. Deft II then starts iconified (to configure with MUI-Prefs if you are registered). Then for each new RAM test: or SD0: (i.e. for each new unarchived archive), I launch, always by a "hotkey" from ToolManager (I like this program :)), a small Arexx script, "DeftII test.rexx". This emptys the list of paths Deft II by replacing them with "RAM:" and "SD0:" and immediately launches after the replacement phase (so localised to RAM: and SD0:). Once This finished, he returns as he had found the list of paths.

In other words, thanks to this small script Arexx and ToolManager, I can perform a very fast replacement (operation in RAM and Post II always iconified) the default tools of each new archive in the test phase, all without losing my configuration of Deft II, it freezes on the partitions from my hard drive.

So I advise you to try this Arexx script, even if you are not a sorcerer of this language (I have put all the necessary comments so you can adapt it to your needs). It automates completely in my opinion the use of Deft II.

several objects in the same file possible.

The advantages of Amiga-E

Amiga-E, already very popular with the amigaphiles, is in a period of rebirth with the compiler ECX of Leif Salomonsson. ECX is fully compatible with EC v3.3a and can generate code 68020 for classic Amiga as well as PowerPC code for MorphOS. An AmigaOne version is not planned but is not excluded either.

No other programming language makes system programming easier than Amiga-E. Among the features that make life easier are:

  • a clear and well structured syntax
  • precompilable modules
  • low level types
  • slight exceptions (they are not objects)
  • immediate lists
  • online assembler

The result is a more fluid style, system programming is safer and more responsible than it is possible with other languages on Amiga.

Normally a good style and careful rereading of the code should avoid the use of Enforcer, MungWall and other system debugging utilities. It is preferable, as far as possible, to prevent rather than cure system programming bugs. Advanced debugging tools can have powers that seem magical, but they still operate at the machine level, that is, at a much lower level than is desirable. There is no better weapon against bugs than a good readability of the source code. Everything that works at a lower level than the source code is too low.

Resource management

As system resources are shared among all programmes, a strategy is needed to ensure the optimal distribution of these resources, which are still too limited. The AmigaOS strategy is fast and simplistic: the first applicant is the first served.

This strategy always guarantees maximum speed, but requires discipline from the programmer to ensure optimal distribution:

  • resources should be allocated as late as possible (at the last moment)
  • resources must be released as soon as possible
  • allowances and discharges must be "parented"

The next chapters explain what "parentheses" means and how the Amiga-E exceptions greatly simplify things.

It should also be borne in mind that:

  • any resource request may succeed or fail
  • the program must support both cases correctly
  • you must inform the user of the origin in case of error

System libraries

As you already know, system features reside mainly in libraries. Some are in ROM, most are in the Libs directory: and others (such as Reqtools and MUI) are not provided by Commodore but are nevertheless part of the Amiga practice and are essential tools for the programmer.

Bookstores are therefore the basic resources and the first thing to know is how to manage them well: If you want to place OPT OSVERSION=37 at the beginning of each program, there is no interest in programming below OS37. A library opens with OpenLibrary(name,version). Specify version=37 for OS2.0+ and version=39 for OS3.0+. Hold the call result in the librarybase variable. If the result is NIL there is nothing else to do but display an error message. Otherwise you can call all the functions of this library. Once you're done you have to call CloseLibrary(librarybase). Then you can no longer call any function of this library.

The reqtools.library is convenient to display error messages, which is why it is very convenient to open it before anything else. The following HelloWorld program illustrates the opening of a bookshop:

OPT OSVERSION=37

MODULE 'reqtools'

PROC hand()
reqtoolsbase:=OpenLibrary('reqtools.library',37)
IF reqtoolsbase
RTEZRequestA('Hello World!','Ok',0,0)
CloseLibrary(reqtoolsbase)
ELSE
PrintF('Could not open reqtools.library!\n')
ENDIF
ENDPROC

The basic variable is "reqtoolsbase" and "RtEZRequestA" displays a simple panel.

Note that success and failure are two distinct and clearly separated cases: In case of failure of OpenLibrary: one displays an error message (and one cannot use reqtools to do so!), one does not close the library. In case of success of OpenLibrary: we can call the reqtools functions, and we have to close the library when we're done.

This is the "parented" management of resources.

Resources and exceptions Amiga-E (resource tracking)

The previous programme is clear but not very realistic. A realistic program includes much more libraries, files and other memory allocations. And this profusion of resources must not be to the detriment of the clarity of the source code. One cannot interlock IFs indefinitely, or even the simplest program will appear abominably tortuous. Fortunately, the Amiga-E exceptions make the structuring of resources invisible. Resource management is becoming even safer, and the program logic is even more transparent.

Here is what the HelloWorld modified for exceptions looks like:

OPT OSVERSION=37

MODULE 'reqtools'

ENUM ERR OK,ERR NOREQTOOLS

Hand PROC() HANDLE
reqtoolsbase:=OpenLibrary('reqtools.library',37)
IF reqtoolsbase=NIL THEN Raise(ERR NOREQTOOLS)
RTEZRequestA('Hello World!','Ok',0,0)
EXCEPT DO
SELECT exception
CASE ERR NOREQTOOLS
PrintF('Could not open reqtools.library v37+!\n')
ENDSELECT
IF reqtoolsbase THEN CloseLibrary(reqtoolsbase)
ENDPROC

This version may seem more complicated than the previous one, but it has a decisive advantage: adding a resource does not alter the structure of the code, it is only the case of an "Open", a "Raise", a "CASE" and an additional "Close".

However, do not use automatic exceptions: they make things implicit, which is usually not a good idea. Make things as explicit as possible.

Programme and environment

A program can be launched either from Shell or from Workbench. Both cases must be managed appropriately. The wbmessage variable allows you to know the launch environment. If the program is started from Workbench then we have wbmessage<>NIL. If the program is started from the Shell then we have wbmessage=NIL.

Of course, if the program is run from Shell then we prefer a message in the console rather than a panel. Wbmessage should be used to distinguish the two cases.

Another Shell expectation is the returned error code:

  • 0 if everything is OK.
  • or 5 for a warning (the program can still continue).
  • or 10 for an error (the program cannot continue).

And here is what the HelloWorld looks like to make the most of the boot environment:

OPT OSVERSION=37

MODULE 'reqtools'

ENUM ERR OK,ERR NOREQTOOLS

Hand PROC() HANDLE
DEF rcode
reqtoolsbase:=OpenLibrary('reqtools.library',37)
IF reqtoolsbase=NIL THEN Raise(ERR NOREQTOOLS)
display('Hello World!')
EXCEPT DO
SELECT exception
CASE ERR NOREQTOOLS
PrintF('Could not open reqtools.library v37+!\n')
rcode:=10
DEFAULT
rcode:=0
ENDSELECT
IF reqtoolsbase THEN CloseLibrary(reqtoolsbase)
ENDPROC rcode

PROC display(msg)
IF wbmessage
RtEZRequestA(msg,'Ok',0,0)
ELSE
PrintF('\s\n',msg)
ENDIF
ENDPROC

Shell arguments

DOS parameters are interpreted by the ReadArgs() function of the back.library, an array of LONGs is provided to ReadArgs(), and in return ReadArgs() stores all DOS parameter values there. Of course you have to call FreeArgs() when we're done.

This simple example displays the MESSAGE provides as shell argument:

OPT OSVERSION=37

ENUM ERR OK,ERR ARGS

DEF myargs:PTR TO LONG,rdargs

Hand PROC() HANDLE
myargs:=[0]
rdargs:=ReadArgs('MESSAGE/A',myargs,NIL)
IF rdargs=NIL THEN Raise(ERR ARGS)
PrintF('\s\n',myargs[0])
EXCEPT DO
SELECT exception
CASE ERR ARGS
PrintF('Bad Args!\n')
ENDSELECT
IF rdargs THEN FreeArgs(rdargs)
ENDPROC

For more information on ReadArgs() and DOS paramers, see Autodocs.

Workbench arguments

Tooltypes are really practical, and even more practical than DOS parameters because they are persistent. So the types of tools are useful even if you start Shell. They provide the basic parameters that Shell user can refine with DOS parameters.

Here's how to read the tool types:

  • open the icon.library
  • Then if we start Shell:
  • get the program path,
  • via GetProgramName() of the back.library
  • Or if we start workbench:
  • 2a. get the directory path <b>wbmessage.arglist.lock</b>,
  • via NameFromLock() of the back library
  • 2b. add the program name <b>wbmessage.arglist.name</b>,
  • via AddPart() of the library back
  • Continue:
  • load the program icon object via GetDiskObject() from icon.library
  • read tool types via FindToolType() of icon.library,
  • non-existent tool types return NIL
  • when finished, release the icon object via FreeDiskObject()

The following code illustrates the entire process, reads the type of MESSAGE tool in the program's .info file, and displays it in the Shell or on the Workbench:

OPT OSVERSION=37

MODULE 'reqtools','icon'
Workbench/startup,workbench/workbench

ENUM ERR OK,ERR NOREQTOOLS,ERR NOICON,ERR NOINFO,ERR NOMESSAGE

DEF prog[80]:STRING
DEF wbmsg:PTR TO wbstartup
DEF diskobj:PTR TO diskobject

Hand PROC() HANDLE
DEF rcode,msg

reqtoolsbase:=OpenLibrary('reqtools.library',37)
IF reqtoolsbase=NIL THEN Raise(ERR NOREQTOOLS)

iconbase:=OpenLibrary('icon.library',37)
IF iconbase=NIL THEN Raise(ERR NOICON)

IF wbmessage
wbmsg:=wbmessage
NameFromLock(wbmsg.arglist.lock,prog,80)
AddPart(prog,wbmsg.arglist.name,80)
ELSE
GetProgramName(program,80)
ENDIF
IF (diskobj:=GetDiskObject(prog))=NIL THEN Raise(ERR NOINFO)

msg:=FindToolType(diskobj.tooltypes,'MESSAGE')
IF msg=NIL THEN Raise(ERR NOMESSAGE)

display(msg)

EXCEPT DO

rcode:=10

SELECT exception
CASE ERR NOREQTOOLS
PrintF('Could not open reqtools.library v37+!\n')
CASE ERR NOICON
display('Could not open icon.library v37+ !')
CASE ERR NOINFO
display('Could not open .info file!')
CASE ERR NOMESSAGE
display('Could not find MESSAGE tooltype!')
DEFAULT
rcode:=0
ENDSELECT

IF diskobj THEN FreeDiskObject(diskobj)
IF iconbase THEN CloseLibrary(iconbase)
IF reqtoolsbase THEN CloseLibrary(reqtoolsbase)

ENDPROC rcode

PROC display(msg)
IF wbmessage
RtEZRequestA(msg,'Ok',0,0)
ELSE
PrintF('\s\n',msg)
ENDIF
ENDPROC

Location

This is the domain of local.library. Locating a program is really not complicated. A catalogue contains all the channels of the program. It is opened by OpenCatalogA() and closed by CloseCatalog(). Meanwhile, all strings are played via GetCatalogStr().

Use EasyCatalog to produce the catalog:

aminet/dev/misc/EasyCatalog.lha

And here's how to locate a HelloWorld:

OPT OSVERSION=37

MODULE 'local'

ENUM ERR OK,ERR NOLOCALE

ENUM CAT HELLO

DEF cat

Hand PROC() HANDLE
localbase:=OpenLibrary('locale.library',38)
IF localbase=NIL THEN Raise(ERR NOLOCALE)
cat:=OpenCatalogA(NIL,'hello.catalog',NIL)
PrintF(GetCatalogStr(cat,CAT HELLO,'Hello World!\n'))
EXCEPT DO
SELECT exception
ERR NOLOCALE CASE
PrintF('Could not open local.library v38+!\n')
ENDSELECT
IF cat THEN CloseCatalog(cat)
IF localbase THEN CloseLibrary(localbase)
ENDPROC

This program could write 'Hello the World!\n' with the appropriate catalogue and 'French' as the selected language. Note that there is no need to quit if OpenCatalogA fails. In this case the program simply uses internal channels.

Important note: if "english" is the selected language then OpenCatalogA will NOT open a catalogue, even if a "english" catalog is present. In this case OpenCatalogA always returns NIL, which is why you must select "French" to test the location.

Task signals (task signals)

Graphical interface applications are driven by events, they are on rest waiting for a signal that reactivates them. A task on rest does not consume any processor power. You can put your program on rest by calling Wait() with events you want to be notified of.

For example, this program is on rest until a "Break" is received by pressing the "Break" button of PriMan v2.0:

OPT OSVERSION=37

CONST SIGNAL BREAK=$1000

PROC hand()
PrintF('sleeping... (use PriMan v2.0 to continue)\n')
Wait(SIGNAL BREAK)
PrintF('running...\n')
ENDPROC

Download PriMan v2.0 here:

aminet/util/moni/Priman20.lha

Later we will see how Wait() can expect other events like window events.

Attribute lists (tag lists)

Attribute lists are a very flexible way to move from parameters to AmigaOS functions. A list of attributes is simply an array of LONGs that always has the following form:

[TAG1,info1,TAG2,info2,...,0]

A capital label indicates which attribute is indicated by the following LONG "info". The "info" is the value of the attribute. The attribute list type is native to Amiga-E.

Note that attribute lists are statically allocated. For dynamically assigned attribute lists you must use NEW:

NEW [TAG1,info1,TAG2,info2,...,0]

The definition of a SCSI disk corresponds to:

REMOVALNAME/K,DEVICE/K,UNIT/N,HKE/K,HKL/K
REMOVALNAME/K - name (not used but future extension).
DEVICE/K - name of the device to which the disc belongs.
UNIT/N - disk unit number.
HKE/K - Ejection call key.
HKL/K - Call key Loading.

REMOVALNAME Zip DEVICE Nexus.device UNIT 6 HKE "ctrl alt f1" HKL "shift ctrl alt f1"

We can't make it any simpler.Some details, though,

  • multi-selection in file selector and possible.
  • the list of modules is saved in DeliTracker format.
  • The most interesting are the Arexx Commands.
  • MODINFO
  • Returns the name of the unit in RESULT.
  • MODNUMINFO <number>
  • Returns to RESULT the name of the module indicated by its list number (0,1,2,..)
  • NBRSMOD
  • Returns the total number of modules in RESULT.
  • NEXTSONG
  • Play the next module.
  • PREDSONG
  • Play the previous module.
  • ADDMOD <name>
  • Add the specifer module to the list.
  • PLAYMOD <name>
  • Play the specified module without adding it to the list.
  • PLAY
  • Play the unit.
  • STOP
  • Stop the listening module.
  • What?
  • Leave ZiqBoom!.
  • CLEARLIST
  • Clear the current module list.
  • LOAD
  • Popup a filerequester to load new modules.
  • HIDE
  • Close the ZiqBoom window!.
  • SHOW
  • Open the ZiqBoom window!.
  • REQINFO
  • Show the query from the File menu.
  • CONFIGLOAD <name>
  • Load the <name> module list.
  • CONFIGSAVE <name>
  • Save the <name> module list.
