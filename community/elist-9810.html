A while back I did this emodule for getting system time..
Setting it must be quite similar I think :)
AmigaE has very good sources about this... I got some good help :)

Hope this helps!

OPT MODULE

MODULE 'devices/timer',
       'exec/ports',
       'exec/io'

EXPORT PROC getSysTime()
DEF secs=0,port:PTR TO mp,tr:PTR TO timerequest
   IF port:=CreateMsgPort()
      IF tr:=CreateIORequest(port,SIZEOF timerequest)
         IF OpenDevice('timer.device',0,tr,0)=0
            tr.io.command:=TR_GETSYSTIME
            DoIO(tr)
            secs:=tr.time.secs
            CloseDevice(tr)
         ENDIF
         DeleteIORequest(tr)
      ENDIF
      DeleteMsgPort(port)
   ENDIF
ENDPROC secs

> Another important note: In C, an int is 4 bytes, in E it is only 2.  You
> shoudl replace all INT's with LONG's, unless you want a C short.

To be exact:

In C it is not defined if an int is 16 or 32 bit. This is completely
compiler
specific.
And this is the cause that "exec/types.c" exists: it defines the macros
LONG,
INT etc. that should always be used when writing C programs on Amiga.

But I think (but this maybe false) most Amiga C compilers use 16 bit (2
bytes) to store an integer (or short integer), 32 bit (4 bytes) to store a
long integer and 8 bit (1 byte) to store a char.

Again: To answer this question correctly have a look in the ANSI-C
definition, there is a range of number of bits each datatype can have.
If you really want to know how many bits/bytes an C datatype has, you must
know for wich compiler it is designed!

It depends on what exactly you want to do.

The simplest is just to use a 1d array of length xsize*ysize and use
y*xsize + x as the index.

If you want it to know its size, you could use something like:-

OBJECT array2d
  xsize
  ysize
  data:PTR TO type
ENDOBJECT

Where data would point to a block of memory with length
xsize * ysize * SIZEOF type.

Alternatively you could just use a list: [ xsize , ysize , data ], where
data could be a simple 1d array, or a list.

Another way is to nest an x array inside each element of a y array, using
the array form of your choice.

HTH

Don't know if I have undestood your question, and I don't have my RKRM
here, however I will try.

Fwrite and Fread are *buffered* functions to access files. They work
differently from Write and Read as they use blocks instead of normal
bytes.
Apart this difference, hoever, there is not difference in their use. You
can just send multiple data out with multiple Fwrite commands, this way:

Fwrite(fh, buf, 4, 3) -> should write 12 bytes that is 3 times 4 bytes
Fwrite(fh, buf+12, 1, 10) -> should write the next 1*10 bytes in buf

and so on.

Remember that the buf pointer must be updated every time you use the
Fwrite function if you are going to write data from the same buffer or you
are going to write always the same data.

The same for Fread, but this time you have to make sure you are not going
to overwrite the same data in the next Fread calls.

Es:

DEF buf[64]:ARRY OF CHAR, tmp=NIL
DEF fh=NIL:filehandle -> You obtain this from an Open() function

tmp:=buf
Fread(fh, tmp, 4, 3) -> We are reading the first 12 bytes from the
                     -> filehandle
tmp := tmp+12        -> Update the position in the buffer
Fread(fh, tmp, 2 ,5) -> Reading the next 5 INT (10 bytes) from the
                     -> filehandle

And go on.

Be ALWAYS sure that you don't go outside the buf size otherwise... well
you know 8).

Remeber also to NEVER use the buffered DOS functions together the
not-buffered function on the same filehandle or you are going to get a
real mess. Probably a Flush() function to flush the OS device buffer
between the passage from the buffer to not-buffered functions and
viceversa should be enough, but I have never tried that (the use of
buffered and unbuffered function on the same file at the same time can be
avoided and, IMHO, must be avoided to not have to solve the problems that
may araise). Moreover buffered functions should always be used when
possible, especially for very small data transerfs (few bytes). They are
much faster (even 5 or more time faster).

Don't know if that may be useful to you. But I hope so.

This line might be the problem.  There's an old bug (that Wouter
doesn't seem able to fix) concerning dereferencing object elements
with no explicit PTR type.  If you're using the typed modules (as
in v3.3a, for example) then this isn't the problem, since "name"
in "wbarg" is explicitly typed as "PTR TO CHAR".

Of course, you could try the following, just in case:

    IF (args.lock) AND (Char(args.name)>0)

>            t:=FindToolType(toolarray, 'FONT')
...
>                    MidStr(t, t, 0,i)
>                    StrCopy(font_name, t, ALL)

This is more likely to be the source of the problem.  "t" is the
result of FindToolType(), which is definitely not an Estring, so
you can't use it as the first argument to MidStr().  In fact, you
don't own that memory (the icon.library does) so you shouldn't be
touching the contents.

Replace the MidStr()/StrCopy() pair of lines with:

  StrCopy(font_name, t, i)

BTW the bizarre use you were making of MidStr() in the example above
is equivalent (for an Estring "t") to:

   SetStr(t, i)

Apart from that the code looks fine.

I have no manuals here, so just some ideas.

>     IF (args.lock) AND (args.name[]>0)

Doesnt args.name always contain the program-name?
And if not, an StrLen(args.name)>0 would be much
clearer, wouldn't it?

>         IF (args[].name<>0) AND (dobj:=GetDiskObject(args.name))

Suspicious. You test args[].name for not being NIL
but use args.name to get the diskobject! And remember
that this is too much C-like. In E, all expression
(even logical ones) are computed. Means that
it evaluates both args.name<>0 and GetDiskObject(args.name)
and then ANDs both results together. So change this
to
        IF args.name<>NIL
                IF dobj:=GetDiskObject(args.name)

>             t:=FindToolType(toolarray, 'FONT')
>             IF t
>                 i:=InStr(t, '/')
>                 temp:=String(StrLen(t))
>                 IF i>3
>                     MidStr(temp, t, i+1, STRLEN-i)
>                     MidStr(t, t, 0,i)
>                     StrCopy(font_name, t, ALL)
>                     font_size:=Val(temp)
>                 ENDIF

Mmmh. A bit overkilled and 'temp' is not freed.
Try:
                IF i>3
                        StrCopy(font_name, t, i)
                        font_size:=Val(t+i+1)
                ENDIF

And did you set all default-values? Maybe you initialize
the start-values for ReadArgs() correctly and therefore
it works in Cli-mode. But when using tooltypes you only
set those values which are given via tooltypes but didn't
initialize those that are missed.

    No daemon is necessary.  The ttf.library adds a new font engine
to the system in the same system-compliant way that is used by the
bullet.library for Compugraphic fonts.  When you install a truetype
font with the included program, it creates the .font and .otag files
that the system uses to determine how to access the font.
    I'm not sure how you'd go about accessing the fonts directly from
your program (off the top of my head, I expect calling OpenDiskFont()
should be enough), but using the ASL font requester provides direct
access to them, and on my A3000/030-25 they are much faster to load than
the Compugraphic variety.
